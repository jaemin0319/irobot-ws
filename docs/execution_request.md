# Claude Code 실행 요청 — MuJoCo FR3 랜덤 reach → home recovery

> 공개 저장소용으로 로컬 사용자명과 홈 절대 경로를 `<user>`, `~`로 가렸습니다. 그 밖의 내용은 원문 그대로입니다.

첨부한 `plan.md`를 바탕으로 실제 작업 PC에서 **환경 재확인 → 구현 → 실제 실행·검증 → 결과 보고**까지 진행하세요. 아래 보완 지시가 원래 계획과 충돌하면 이 요청문을 우선하세요. 다시 계획만 제출하고 멈추지 말고, 작업공간 안에서 필요한 준비와 구현을 진행하세요.

## 1. 검토 결론과 유지할 목표

계획의 주요 단계는 빠짐없이 들어 있습니다.

| 원래 목표 | 계획에 포함된 내용 | 실행 시 유지할 조건 |
|---|---|---|
| 공식 모델 확보 | §3 공식 저장소·버전·메시·라이선스·변환·모델 검사 | 실제 원본 파일과 확보 결과로 재확인 |
| 초기 home 확인 | §3.3 home 유지 검사, §4.4 HOME_CHECK | 실제 관절 위치·속도로 판정 |
| 고정 목표 최초 검증 | §5 단계 5 fixed 모드 | reach와 실제 제어 복귀 모두 통과한 뒤 랜덤 반복 진행 |
| 유효한 새 랜덤 목표 | §4.3 매 사이클 샘플링·IK·충돌·경로 검사 | 고정 목록 반복 금지, 유효 목표 생성 실패 시 중단 |
| 실제 제어 recovery | §4.1 토크 제어·관절 궤적 | live 상태 reset·qpos 대입으로 복귀 대체 금지 |
| 복귀 확인 뒤 다음 목표 | §4.2 RECOVER_SETTLE 성공 → GEN_TARGET | 상태 전이와 이벤트 로그로 증명 |
| 무한 반복·종료·실패 처리 | §4.5–4.7, §6 | 기본 실행은 무제한, 실패 시 다음 단계 금지, 사용자 종료 정상 처리 |

필수 최종 순서:

**모델 로드 → 초기 home 확인 → 새 유효 랜덤 목표 생성 → reach → 도달 확인 → recovery → home 복귀 확인 → 다음 새 랜덤 목표 생성 → 반복**

현재 계획의 FR3 + 고정 Franka Hand, TCP 아래 방향·yaw 자유, SRDF ready home, 목표 범위·허용 오차·주기·제어기를 구현의 출발점으로 사용하세요. 원래 사용자 요구에서 직접 정하지 않았던 값과 기존 Claude 세션에서 확인된 결정을 구분해 기록하세요. 모델·실행 결과로 기술적 설정을 조정할 수 있으나, 원래 동작과 성공 판정 원칙은 유지하세요.

## 2. 구현에 반드시 반영할 보완

### A. 복귀 경로를 실제 상태에서 다시 확인

계획 §4.3의 “recovery는 같은 경로의 역방향이므로 함께 통과”는 충분하지 않습니다. reach 성공 시 실제 q는 IK 목표 q와 조금 다를 수 있고, home 성공 시에도 실제 q는 home 값과 정확히 같지 않을 수 있습니다.

- reach와 recovery 모두 **각 동작 시작 시 실제 q·q̇**를 읽으세요. 경로 검사에서 현재 q를 home 값으로 치환하지 마세요.
- recovery 시작 직전에 실제 상태에서 home까지의 궤적을 만들고 관절 제한·충돌·여유 거리를 다시 확인하세요.
- 시작 속도를 0으로 가정할 경우 실제 속도와의 불연속을 평가하고, 필요하면 측정 속도를 반영한 quintic 경계조건을 사용하세요. 상태를 직접 0으로 만들지 마세요.
- 고정 50점 검사는 검사 간격·최소 여유 거리와 함께 평가하세요. 간격 사이에서 충돌을 놓칠 가능성이 있으면 관절 변화량에 따라 샘플을 더 촘촘히 하세요. 유한 샘플 검사를 연속 경로 안전성의 수학적 보장이라고 보고하지 마세요.
- 추종 중에도 실제 상태의 관절 제한·충돌·오차를 감시하세요. recovery 경로가 유효하지 않으면 FAILED로 중단하고 다음 목표를 생성하지 마세요.

### B. 모델 변환 결과를 직접 검사

- sparse checkout 파일 목록을 확정하기 전에 Xacro include, YAML, 패키지 참조, 메시의 의존성을 실제로 추적하세요. 계획에 적힌 파일만으로 충분하다고 가정하지 마세요.
- 전개된 URDF의 위치에서 모든 메시 경로가 실제 파일로 해석되는지 확인하세요. `meshdir`, 파일의 상대 경로, URDF→MJCF 저장 위치가 겹쳐 `meshes/meshes/...`처럼 잘못되지 않도록 일관된 규칙을 사용하세요.
- DAE를 재질별 여러 OBJ로 나누면 모델이 **모든 조각**을 참조하도록 수정하세요. 확장자만 바꾸는 방식으로 누락시키지 마세요. scene transform, 단위·scale, 축 방향, 링크별 visual/collision origin을 보존하고 확인하세요.
- visual geom은 `contype=0`, `conaffinity=0`으로 충돌에서 제외하고 collision geom은 필요한 충돌이 실제 활성화되도록 설정·검사하세요. `group` 번호만으로 충돌 설정을 대신하지 마세요.
- 충돌 제외 쌍은 SRDF 실제 내용을 확인하여 반영하고, 무조건 인접 링크만 제외하거나 모든 자기충돌을 끄지 마세요. 의도적으로 겹치는 검증 자세 등으로 충돌 검출이 작동하는지 확인하세요.
- 바닥·베이스 위치와 허용 접촉을 명시하세요. 베이스 설치를 위해 정상적인 고정 접촉이 필요한 경우 허용 쌍과 위험 접촉을 구분하세요. `ncon=0`을 얻으려고 로봇이나 바닥을 근거 없이 옮기지 마세요. world=base 가정도 실제 장면과 대조하세요.
- 손가락을 고정할 때 관절을 제거하는 것뿐 아니라 0.04 m 개방 상태의 transform, 질량·관성을 보존하세요. TCP 이름·offset은 Xacro 전개 결과와 독립 FK로 확인하세요.
- 질량, 무게중심, 관성 텐서를 동일 좌표계로 비교하고 모델 보완 때문에 원본 inertial이 메시 추정값으로 바뀌지 않았는지 검사하세요.
- 액추에이터 이름·관절 매핑, gear, 토크 단위·제한을 검사하세요. armature의 `motor_inertia × gear²` 적용 여부는 원본 YAML의 정의·단위를 확인한 뒤 결정하여 중복 환산을 피하세요. 제안 damping·armature·게인은 공식 확정값으로 표시하지 마세요.
- DAE 변환 실패 시 STL visual 대안은 사용할 수 있으나 형상·외관 제한을 보고하고, GUI에서 팔·손·마커가 정상적으로 보이는지 확인하세요.

### C. 실제 실행 환경·용량 확인

계획의 `[확인]`은 이전 조사 기록입니다. 실행 시 다시 확인하세요. 특히 MuJoCo 3.15.0의 배포 여부·Python 호환 wheel, 공식 모델 태그·커밋, 1.1 GB 여유 공간을 현재 사실로 그대로 사용하지 마세요.

- 실제 사용자 홈 아래 `~/irobot_ws`를 사용하세요. `~`은 현재 사용자·홈 확인 결과가 같을 때만 사용하세요.
- 작업공간이 이미 생겼다면 먼저 내용·지침·권한을 확인하여 재사용하고 기존 파일을 보호하세요. 없으면 이제 생성하세요. 심볼릭 링크 등 예상과 다른 경로면 실제 대상을 확인하고 함부로 바꾸지 마세요.
- Python, venv, pip, xacro, GPU·DISPLAY·GLFW/GLX, 네트워크와 의존성 상태를 다시 확인하세요. Python 실행·변환·검증 모두 일관된 격리 환경을 사용하세요. ROS 환경은 Xacro 전개에 필요한 범위만 적용하세요.
- MuJoCo 3.15.0 사용이 가능하면 고정하고, 불가능하면 공식 배포·호환성 근거에 따라 사용할 버전을 선택해 이유를 기록하세요. 단순히 “직전 마이너”라고 추측해서 설치하지 마세요.
- 설치·다운로드·변환의 **최종 크기와 최대 임시 사용량**을 추정하세요. 설치 전 조건은 계획의 700 MB 하한에 더하여 `예상 추가 최대 사용량 + 남겨 둘 여유 공간`을 만족해야 합니다. 최종 설치 용량만 보고 통과시키지 마세요.
- 준비 단계에서도 용량을 확인하고, 실행 중 확인 간격은 실제 소비 속도에 맞추세요. 작업공간의 임시 파일만 정리하세요. 공간이 부족하면 구체적인 부족량과 필요한 조치를 보고하고, 작업공간 밖 캐시 삭제·다른 디스크 이동·시스템 변경을 임의로 수행하지 마세요.
- 시스템 드라이버·ROS 설치를 변경할 필요가 없다면 기존 것을 사용하세요. 프로젝트 코드, venv, 모델·메시, 문서, 로그, 캐시·임시 산출물은 `~/irobot_ws` 안에 관리하세요.

### D. 상태 판정·실패·뷰어 입력 처리

- 초기화 때 live qpos=home, qvel=0 설정은 허용합니다. 초기화 이후 live qpos/qvel 직접 변경·reset·keyframe 복원으로 reach나 recovery를 수행하지 마세요. IK·경로 검사 전용 scratch MjData 변경과 테스트 전용 실패 주입은 명확히 분리하세요.
- 성공 조건은 계획 §4.4의 위치·방향·관절·속도 오차와 연속 유지 시간입니다. 유지 조건이 깨지면 타이머를 초기화하세요. 시간 초과는 실패 조건입니다.
- runtime의 제한·접촉·수치 이상 검사를 REACH/RECOVER뿐 아니라 HOME_CHECK와 모든 SETTLE 상태에도 적용하세요.
- 다음 목표 생성 함수는 최초 HOME_CHECK 성공 또는 RECOVER_SETTLE 성공 경로에서만 호출하세요. 종료·실패 상태에서는 호출되지 않게 하세요. 사이클 ID와 `HOME_CONFIRMED`, `TARGET_GENERATED`, `REACH_CONFIRMED`, `RECOVERY_STARTED`, `RECOVERY_CONFIRMED` 이벤트 순서를 남기세요. 후보 거부 기록과 유효 목표 확정 이벤트도 구분하세요.
- GUI reset·관절 슬라이더·제어 입력·마우스 perturbation이 실제로 어떻게 반영되는지는 설치한 MuJoCo 버전의 공식 API와 실행 결과로 확인하세요. `data.time` 감소 하나만으로 모든 외부 상태 변경을 감지한다고 가정하지 마세요. 필요하면 GUI에 별도 표시용 데이터를 사용하거나 상태 변경을 차단·감지하는 구조를 택하세요. 카메라 조작은 가능하게 두세요.
- reset 또는 외부 상태 변경을 감지하면 더 움직이기 전에 FAILED로 중단하세요. viewer sync와 공유 시각화 상태의 lock 사용은 설치 버전 문서에 맞추세요. “오버레이는 lock 밖에서 갱신”을 무조건 적용하지 마세요.
- 2 s 시뮬 정지 감지는 정상적인 GEN_TARGET의 계산과 구분하세요. IK·후보 검사·경로 검사 내부에서도 종료 요청을 확인하여 3 s 계산 제한 때문에 종료가 지연되지 않게 하세요. 연산 자체가 멈추면 동일 루프의 검사만으로 감지 가능한지 평가하세요.
- 실패하면 해당 실행의 자동 반복을 정지하고 상태·오차·원인을 기록하세요. 다음 단계 진행, 다음 목표 생성, 자동 reset·자동 home 복귀는 금지합니다. 실패를 보존한 뒤 Claude가 코드를 수정하고 새 검증 실행을 시작하는 것은 가능합니다.
- 정상 실행 중 창 닫기·Ctrl+C·SIGTERM은 정상 종료(exit 0), FAILED 후 종료는 실패 종료(exit 1), 검증 하네스의 정상 관측 종료는 성공으로 명확히 구분하세요. 실패 정지 중에도 창 닫기·종료 입력을 처리하세요.
- 게인 0 실패 주입은 timeout보다 추종 오차 실패가 먼저 발생할 수 있습니다. 각 실패 경로를 실제로 유발하는 독립적인 테스트를 구성하고 원래 예상한 원인과 다른 실패를 통과로 처리하지 마세요.

### E. 저장 위치·전체 로그 제한

- 계획의 `~/plan.md` 백업·교체와 작업공간 밖 메모리 파일 변경은 이 구현에 필요하지 않습니다. 수행하지 말고 입력 계획과 이 요청문을 `~/irobot_ws/docs/`에 보존하세요.
- 실행별 이름의 RotatingFileHandler 하나를 25 MB로 제한해도 과거 실행 파일과 `failure_*.json`이 쌓일 수 있습니다. **logs 디렉터리 전체**를 대상으로 보존 정책을 구현하세요. 일반 실행 로그 예산과 최신 실패 기록·모델 검사·결과 요약의 예산을 합쳐 명시하고 제한하세요.
- 프로젝트에서 생성한 오래된 로그만 정리하고 최신 실패·최종 검증 증거는 보존하세요. 기존 사용자 파일을 삭제하지 마세요.
- `docs/CURRENT_STATE.md`에 진행 상황과 막힌 원인을 기록하고, 최종 결과는 `docs/RESULTS.md`에 남기세요.

## 3. 구현·실행 순서와 통과 기준

각 단계의 실제 결과를 확인한 뒤 다음 단계로 진행하세요.

1. **사전 점검과 작업공간 준비**
   - 사용자·홈·권한·현재 내용·용량·환경 재확인.
   - 작업공간과 전용 venv 준비, 호환 의존성 설치·버전 고정.
   - 기준을 충족하지 못하면 원인과 필요한 조치를 보고하세요.

2. **공식 모델 확보 및 검사**
   - 공식 `frankarobotics/franka_description`의 실제 태그·커밋·의존성 확인 후 확보.
   - Xacro→URDF→메시 변환→MJCF 보완. 출처·LICENSE·NOTICE·해시·변환 기록 보존.
   - 계획 §3.3과 위 보완 B의 모델 검사 통과. 실패 항목은 해결하고 다시 확인하세요.

3. **뷰어·초기 home 검증**
   - 로봇·목표 마커 표시를 실제 GUI로 확인하세요.
   - 초기 home 상태 판정과 중력 보상·제어 유지 검증을 통과하세요. FK 기준도 확인하세요.
   - GUI 접근이 없으면 헤드리스 결과와 GUI 미검증을 분리해 보고하고, GUI 성공으로 표시하지 마세요.

4. **고정 목표 한 점 검증**
   - 계획의 TCP (0.45, 0.20, 0.35) m, 아래 방향 목표를 실제 IK·경로 검사로 검증하세요.
   - 유효하지 않으면 이유와 새 검증 목표를 기록하세요.
   - reach → 상태 판정 → 실제 상태에서 복귀 경로 검사 → 토크 recovery → home 상태 판정을 1회 끝까지 실행하세요.
   - 실제 도달 오차, 방향 오차, 속도, home 관절 오차, 접촉·토크 포화·경고를 기록하세요. 통과 전 랜덤 반복으로 넘어가지 마세요.

5. **랜덤 목표 무한 반복 구현 및 검증**
   - 기본 `./run.sh`는 최대 사이클 수 없이 실행되도록 구현하세요. RNG를 시작 때 한 번 생성하고 실제 사용한 seed를 기록하세요.
   - 계획의 목표 범위를 출발점으로 사용하고 IK·경로 검사 결과로 채택률과 거부 원인을 평가하세요. 채택 목표는 유효성 필터 때문에 원래 상자 전체의 균일 분포와 달라질 수 있음을 기록하세요.
   - 계획의 50 후보/3 s 상한은 실제 PC에서 시간·성공률을 측정한 뒤 사용하세요. 종료 요청을 받을 수 있어야 하며 실패를 숨기려고 무제한 재시도하지 마세요.
   - 헤드리스 검증은 계획대로 시뮬레이션 30분 상당 또는 100 사이클 중 하나의 관측 기준을 명시해 완료하세요. 어느 기준을 사용했고 실제로 몇 사이클을 완료했는지 보고하세요. 동일 기본 제어·목표 생성·판정 로직을 사용하세요.
   - GUI에서 최소 10사이클을 실행하여 표시와 동작을 확인하세요. 유한 관측은 외부 검증 하네스가 종료 요청을 보내는 방식으로 수행하고, 제품 기본 실행에 반복 제한을 넣지 마세요.
   - 전 사이클에 대해 `RECOVERY_CONFIRMED(k)`가 `TARGET_GENERATED(k+1)`보다 앞서는지 검사하세요. qpos 직접 복귀·자동 reset이 없다는 코드 확인과 실제 관절 변화·제어 입력 기록을 함께 제시하세요.

6. **실패·종료·로그 제한 검증**
   - timeout, 유효 목표 생성 고갈, 수치 이상, 외부 reset/상태 변경을 구분해 시험하세요.
   - 실패 뒤 상태 전이가 멈추고 신규 목표 이벤트가 없는지 확인하세요.
   - 정상 REACH·RECOVER·GEN_TARGET 및 FAILED 정지 상태에서 종료 동작을 확인하세요. 정상 종료는 목표 1 s 이내이며 실제 측정값과 종료 코드를 기록하세요.
   - 반복 실행을 포함해 전체 로그 보존 제한과 자원 정리를 확인하세요.

## 4. 변경과 문제 해결 원칙

- 구현 세부 선택, 모델 변환 수정, 의존성 조정, 게인·궤적 시간 조정은 필요한 범위에서 진행하고 이유를 문서화하세요.
- 실패한 실행은 실패로 남기고, 원인을 수정한 뒤 새 검증 실행을 수행하세요. 모든 기존 검증을 이유 없이 반복하지 말고 변경으로 영향을 받은 검증을 다시 수행하세요.
- 성공으로 보이게 하려고 허용 오차를 넓히거나 충돌 검사를 끄거나 실패를 건너뛰지 마세요. 목표 범위를 좁히거나 판정 기준을 변경해야 한다면 실제 결과와 변경 전후 값을 설명하세요. 최초 목표를 실질적으로 바꾸는 변경은 사용자에게 확인하세요.
- 실제 환경 때문에 완료할 수 없는 부분이 있으면 가능한 독립 작업은 마무리하고, 막힌 정확한 단계·오류·시도·사용자에게 필요한 조치를 보고하세요. 미실행 항목을 검증 완료라고 쓰지 마세요.
